격자에서 거리로 — 점수 계산 방식을 바꾸려는 이유

H3 육각 격자를 빼고 PostGIS 거리 계산으로 바꾸는 근거

루디 도보망 그래프(길 조각 223,664개)의 실제 값으로 계산했습니다. 시설 좌표는 이 문서에 없어서, 방식 차이를 보여주는 패널에만 가상 시설 9개를 썼습니다(명시).

한 줄로 지금은 "같은 칸에 있나"로 점수를 매깁니다. 바꾸려는 건 "실제로 몇 미터 떨어졌나"로 매기는 것입니다. 같은 데이터로 계산했을 때 구별되는 값이 3개에서 252개로 늘어납니다.

0먼저 용어 정리 — GiST는 방식이 아니라 도구입니다

헷갈리기 쉬운 지점입니다. 바뀌는 건 두 층입니다.

GiST는 "거리 계산을 빠르게 해주는 색인"입니다. 격자의 대안이 아니라, 거리 계산을 실용적인 속도로 만들어 주는 장치입니다. 그래서 정확히 말하면 "격자 방식 → 거리 방식"이고, GiST는 후자를 가능하게 하는 도구입니다.

3격자의 두 번째 문제 — 경계

격자 방식은 거리를 아예 보지 않습니다. 칸 번호만 비교합니다. 그래서 이런 일이 생깁니다.

칸 밖이라 안 세어짐 같은 칸이라 세어짐

20m 떨어진 CCTV가 칸 경계 너머에 있으면 안 세어지고, 340m 떨어진 CCTV가 같은 칸이면 세어집니다. 물리적 거리와 무관하게 잘리는 것이라, 사람이 보면 납득할 수 없는 결과가 나옵니다.

거리 방식에서는 이 문제가 정의상 존재하지 않습니다. 기준이 거리 하나뿐이니까요.

4GiST가 하는 일

"모든 길 × 모든 시설의 거리를 다 계산하면 너무 느리지 않나" — 맞습니다. 길 223,664개 × 시설 수만 개면 몇 십억 번입니다.

GiST 인덱스가 이 문제를 2단계로 해결합니다. 데이터베이스가 알아서 합니다.

1단계에서 사각형 박스로 후보를 빠르게 추리고, 2단계에서 추려진 것만 정확한 거리를 계산합니다. 박스는 원보다 넓게 잡히므로 진짜 후보를 놓치지 않습니다. 넓게 잡은 만큼 2단계 계산이 조금 늘어날 뿐, 최종 결과는 전부 다 계산한 것과 완전히 같습니다.

SELECT e.link_id,
       SUM(1 - ST_Distance(e.geom, c.geom) / 150.0) AS 안전_원점수
FROM   walk_edges e
JOIN   cctv c ON ST_DWithin(e.geom, c.geom, 150)
GROUP  BY e.link_id;

그리고 이건 수집 단계에서 한 번만 돌리는 배치 작업입니다. 사용자 요청 때 도는 게 아니라, 데이터가 갱신될 때만 돕니다. 몇 분 걸려도 문제가 없습니다.

이미 우리 코드가 쓰고 있습니다. graph_repository, edge_repository, running_repository 세 곳에서 ST_DWithin을 호출합니다. 즉 "공간 쿼리를 다룰 줄 몰라서 격자를 썼다"가 아니라, 점수 계산 쪽만 격자로 남아 있는 상태입니다.

GiST · R-tree · KD-tree 관계 — 선택지가 사실 하나입니다

GiST는 그 자체로 하나의 인덱스가 아니라, 원하는 자료구조를 얹을 수 있는 틀(프레임워크)입니다. 그리고 PostGIS의 공간 인덱스는 그 틀 안에 R-tree를 구현한 것입니다. 옛 PostgreSQL에는 독립 rtree 타입이 따로 있었는데, 동시성·장애복구 지원이 약해서 폐기되고 GiST 안으로 흡수됐습니다.

그래서 "GiST를 쓸까 R-tree를 쓸까"라는 선택은 존재하지 않습니다. GiST를 쓰는 것이 곧 R-tree를 쓰는 것입니다.

"k-ring 사전필터는 육각형으로 반경을 근사하니 부정확하다"는 설명은 틀렸습니다. 사전필터는 넉넉히(반경보다 넓게) 잡으면 진짜 후보를 놓치지 않고, 정확도는 2단계가 결정합니다. 대가는 정확도가 아니라 속도와 코드 복잡도입니다. 반대할 근거는 "부정확"이 아니라 "중복"이어야 합니다.

단, 같은 셀만(k=0) 보는 사전필터는 실제로 부정확합니다 — 경계 너머 후보가 2단계에 도달하지 못하니까요.

우리는 둘 다 아닙니다. CCTV와 도로가 같은 PostgreSQL 안에 있고, 이 계산은 미리 한 번 돌리는 배치입니다.

6우리 저장소가 이미 사례입니다

확인됨 새로 도입하는 게 아닙니다. 이 방식이 이미 프로덕션 코드에서 돌아가고 있고, 인덱스까지 만들어져 있습니다.

route_poi_repository.py가 만드는 인덱스입니다.

CREATE INDEX IF NOT EXISTS idx_route_pois_geom  ON route_pois  USING GIST(geom);
CREATE INDEX IF NOT EXISTS idx_route_pois_geog  ON route_pois  USING GIST ((geom::geography));
CREATE INDEX IF NOT EXISTS idx_walk_edges_geog  ON walk_edges USING GIST ((geom::geography));
CREATE INDEX IF NOT EXISTS idx_walk_nodes_geog  ON walk_nodes USING GIST ((geom::geography));

geom::geography 캐스팅용 함수 인덱스가 이미 걸려 있습니다. 코드 주석에 이유까지 적혀 있습니다 — "geometry 인덱스만 있으면 geom::geography ST_DWithin 조인에서…". 즉 팀이 이 함정을 이미 알고 해결해 뒀습니다.

그리고 같은 파일이 이미 이렇게 동작합니다.

ST_Distance + ST_DWithin 으로 시설의 최근접 도보 Edge를 찾는다
   → nearest_edge_id 를 갱신한다
   → GROUP BY nearest_edge_id 로 Edge별 개수를 집계한다
   → toilet_count / transit_count / accessibility_poi_count
따라서 화장실·정류장·엘리베이터는 이미 거리 방식이고, CCTV·상권·랜드마크만 격자 방식으로 남아 있습니다. 바꾸는 일은 새 아키텍처 도입이 아니라, 같은 저장소 안의 두 방식 중 하나로 통일하는 것입니다.

7성능 근거

최근접 지점 탐색 — Crunchy Data 실측 (밀리초)
인덱스 없음14,252 ms

PostgreSQL 관리 서비스 회사 Crunchy Data의 실측입니다. 인덱스 없이 최근접 지점을 찾으면 약 14초, GiST 인덱스를 쓰면 7.8밀리초 — 약 1,800배 차이입니다.

그리고 PostGIS 공식 문서는 geometry/geography 컬럼을 만들면 GiST 인덱스부터 걸라고 표준 관행으로 명시합니다. 선택 사항이 아니라 기본입니다.

8주의 — "상용 지도 서비스도 쓴다"는 근거가 아닙니다

확인 결과
구글맵·카카오맵·네이버지도의 도보 길찾기 엔진이 PostGIS를 쓴다고 입증할 공개 근거는 없습니다. 셋 다 API 계약과 옵션은 공개하지만 내부 저장소와 탐색 엔진은 공개하지 않습니다.

아래 사실들은 근거가 아닙니다. 혼동하기 쉬운 지점입니다.

✕  카카오클라우드가 PostgreSQL·PostGIS를 지원한다
✕  네이버클라우드가 PostgreSQL·PostGIS를 지원한다
✕  PostGIS가 Google encoded polyline 형식을 만들 수 있다
✕  개인 블로그의 시스템 설계 글이 Google Maps 저장소를 PostGIS로 가정한다

이건 클라우드 고객에게 기능을 제공한다거나 출력 형식이 호환된다는 뜻이고, 그 회사가 길찾기 내부에서 PostGIS를 쓴다는 뜻이 아닙니다.

PostGIS를 쓴다고 경로 탐색까지 DB에서 하는 게 아닙니다. 대형 서비스도 저장·전처리는 공간 DB로 하면서 탐색은 별도 메모리 그래프 엔진으로 할 수 있습니다. 루디도 같은 구조입니다.

그래서 우리 근거는 이렇게 써야 합니다

루디의 CCTV·공원·화장실 데이터와 서울시 도보 네트워크는 같은 PostgreSQL에 저장되어 있다. 이 데이터는 실시간으로 움직이는 대상이 아니라 일정 주기로 갱신되는 시설·환경 데이터이므로, 사전 배치 작업에서 PostGIS의 거리·교차 연산과 GiST 공간 인덱스로 기존 도보 Edge에 속성을 부착할 수 있다. 실제 경로 생성은 이렇게 구성된 도보 Graph와 탐색 알고리즘이 담당한다.

근거가 되는 것
   ○  데이터가 같은 PostgreSQL에 있다
   ○  공간 데이터가 자주 변하지 않는다
   ○  요청마다 결합할 필요 없이 미리 계산할 수 있다
   ○  셀 단위 근사보다 실제 거리·도형 관계가 필요하다
   ○  PostGIS와 GiST로 그 계산을 할 수 있다
   ○  우리 저장소에 이미 그 인덱스와 코드가 있다

9데이터 형태마다 연결 방식이 달라야 합니다

지금은 모든 데이터를 H3 하나로 처리합니다. 그런데 원본의 공간 형태가 다릅니다.

데이터 형태예시권장 연결 방식지금
PointCCTV, 화장실, 가로등최근접 거리 + 반경 내 개수H3 (화장실만 거리)
Polygon공원, 녹지, 그늘Edge와 겹치는 길이·포함 비율이미 적용됨 (park_overlap_ratio)
Line보행로, 경사 구간기존 Edge와의 선형 중첩미적용
측정 Point소음·대기 측정소거리 가중 보간 또는 최근접 관측값미적용
행정구역 통계범죄·인구 통계행정구역 교차 + 별도 신뢰도 표시미적용
Line 데이터를 Edge로 추가하면 안 됩니다
경사나 공원 데이터가 별도의 Line이라는 이유로 도보 가능한 길로 Graph에 추가하면, 실제 도보망에 없는 직선 Edge가 생깁니다. 길이 존재하는지는 도보 네트워크만 결정하고, 테마 데이터는 기존 Edge에 속성만 부착해야 합니다.

10점수로 합치기 전에 원시 특성을 보존합니다

지금은 CCTV 개수를 곧바로 safety_score 하나로 압축합니다. 중간 사실이 남지 않아서 나중에 검증할 수가 없습니다.

지금:   CCTV 좌표  →  H3 셀 개수  →  safety_score 0.4816
                                      ↑ 원래 몇 대였는지 알 수 없다

바꿈:   CCTV 좌표  →  cctv_count_50m        = 1
                      cctv_count_100m       = 3
                      cctv_count_200m       = 9
                      nearest_cctv_distance_m = 37.2
                          ↓  별도의 조합 정책에서
                      safety_score

관측된 사실을 먼저 보존하고, "어떤 값이 안전을 얼마나 설명하는지"는 별도 단계에서 결정합니다. 이러면 반경을 바꿔볼 수 있고, 가중치를 실험으로 정할 수 있고, 점수가 이상할 때 원인을 추적할 수 있습니다. 지금은 0.4816이라는 숫자만 남아서 무엇 때문에 그 값인지 되짚을 수 없습니다.

왜 "항목마다 다른 반경"이 중요한가

세 항목이 서로 다른 질문을 던지고 있는데, 격자는 전부 363m로 통일해 버립니다.

CCTV      "이 길을 실제로 비추는가"      →  가까워야 의미 있다   (150m)

랜드마크   "볼 만한 것이 있는가"          →  멀리서도 보인다      (300m)

정규화를 왜 같이 바꾸나

지금:   log(개수+1) ÷ log(서울 전체 최대 개수+1)
        → CCTV 한 대가 추가되면 최대값이 바뀌어
          서울 모든 길의 점수가 조금씩 다 바뀐다
        → 어제 실험과 오늘 실험을 비교할 수 없다

바꿈:   min(1, 원점수 ÷ 고정 포화값)
        예: "반경 150m 거리가중 합이 5.0이면 만점"
        → 데이터가 늘어도 다른 길 점수는 그대로

반경 150m는 물리적으로 의미가 명확한 크기라 "몇 대면 충분한가"를 정할 수 있습니다. 육각형 칸은 위치마다 크기가 다르고 363m라 그 판단이 애초에 불가능했습니다.

12그냥 바꾸면 안 됩니다 — 반경이 관건

함정 — 반경 50m는 점수를 죽입니다
처음엔 "반경 50m"를 생각했는데, 면적을 계산해 보니 H3 res 10 셀보다 작습니다. res 10에서 CCTV가 없는 셀이 52%였던 그 문제가 그대로 재발합니다. 해상도만 올리고 데이터를 비워버리는 것이라, 안 하는 것보다 나쁩니다.
반경버퍼 면적기대 CCTV0이 될 비율
50 m0.011240.64대52.8%
80 m0.025531.45대23.5%
100 m0.038192.17대11.4%
150 m0.080854.59대1.0%
200 m0.139227.90대0.0%

서울 CCTV 밀도 약 56.8대/km²(현재 안전 점수에서 역산), 길 조각 길이 중앙값 33.9m 기준. 균일 분포를 가정한 낙관적 추정이며, 실제로는 시설이 몰려 있어 0인 비율이 더 높습니다.

반경 150m의 버퍼 면적이 현재 육각형 칸 면적과 비슷합니다. 즉 데이터 희소성은 지금과 같은 수준인데, 해상도는 길 조각 단위가 됩니다.

같은 면적인데 왜 더 좋은가 — 고정된 칸 vs 움직이는 창

[격자]   ┌────────칸────────┐        길 A, B, C 가 같은 칸
         │  ━A━  ━B━  ━C━   │        →  A = B = C  (계단식)
         └──────────────────┘

[거리]      ╭──A의 창──╮
               ╭──B의 창──╮          창이 길마다 움직인다
                  ╭──C의 창──╮       →  A ≠ B ≠ C  (연속적)
         ━A━  ━B━  ━C━

칸은 고정돼 있어 안에 있는 길이 전부 같은 값을 받습니다. 창은 길마다 따라 움직이므로 20m 옆 길은 창도 20m 움직여 값이 조금 다릅니다. 같은 양의 데이터로 훨씬 세밀한 점수가 나오는 이유가 이것입니다.

그래서 개수 대신 거리 가중을 씁니다

개수 세기     10m 시설 = 1,   140m 시설 = 1      (같게 취급)
거리 가중     10m 시설 = 0.93, 140m 시설 = 0.07   (가까울수록 크게)

반경을 넉넉히 잡아 희소성을 없애면서도, 멀리 있는 시설이 결과를 지배하지 않습니다. Green Paths와 Trail Router 같은 실제 서비스가 쓰는 방식이고, 통계에서 커널 밀도라고 부릅니다.

13남은 확인 사항과 H3의 자리

정정 이 문서의 앞선 초안에서 저는 "geography 캐스팅 때문에 GiST 인덱스가 안 걸릴 수 있다"고 경고했습니다. 확인 결과 그 경고는 틀렸습니다. route_poi_repository.py가 이미 idx_walk_edges_geog, idx_walk_nodes_geog를 ((geom::geography)) 함수 인덱스로 만들어 두었습니다. 팀이 이 함정을 이미 알고 해결해 뒀습니다.

그래도 배포 환경에서 인덱스가 실제로 존재하는지는 한 번 확인할 값어치가 있습니다 — 인덱스 생성 코드가 호출되는 시점에 달려 있기 때문입니다.

SELECT indexname, indexdef FROM pg_indexes
WHERE  tablename IN ('walk_edges','walk_nodes','route_pois');

선택지가 하나 더 있습니다. 서울 규모라면 미터 좌표계(EPSG:5186 등) 컬럼을 따로 두는 방식이 가장 빠릅니다 — 거리 계산이 곡률 보정 없는 단순 평면 연산이 되기 때문입니다. 다만 이미 있는 geography 인덱스로 충분한지 먼저 재보고 결정하는 게 순서입니다.

H3를 어디에 남기나

완전히 제거해야 하는 건 아닙니다. 용도가 다릅니다.

용도H3가 적합한가
경로 비용 점수부적합. 363m 해상도로 34m 단위 선택을 다룰 수 없다 — 이 문서 전체의 내용
지역별 분포 시각화 · 히트맵적합. 363m 해상도가 오히려 알맞다. 얇은 도로선보다 벌집 히트맵이 직관적이다
대략적 통계 집계 (구별 안전 지수 등)적합
서로 다른 시스템 간 공통 공간 키적합 (우리는 해당 없음 — 같은 DB)
실시간 대규모 객체 처리적합 (우리는 해당 없음 — 배치)
거리 계산 사전 필터불필요. GiST가 이미 한다 (§5)

즉 "정밀 계산은 PostGIS, 시각화는 H3"라는 역할 분담은 타당합니다. 다만 그건 H3를 점수 계산에서 빼는 것을 전제로 성립합니다 — 지금은 점수 계산에 쓰고 있습니다.

H3 시각화를 근거로 쓸 때 정정할 숫자 세 가지
흔히 인용되는 값실측·정정
res 9 한 변 길이174 m서울 실측 168 m (전 지구 평균 201 m). 174 m는 중심에서 변까지의 거리이며 H3 v3 문서의 오표기가 v4에서 정정됨
서울을 덮는 셀 수약 5,700개6,407개 (도보망이 있는 곳만)
"3~4분 보행 리듬과 일치"—근거 없음. 168 m는 도보 약 2.5분, 최대 폭 363 m는 약 5.4분. 사후 정당화로 보인다

그리고 "1cm의 오차도 허용하지 않는다" 같은 표현은 피하는 게 좋습니다. PostGIS의 거리 계산은 정확하지만, 최종 점수의 정확도는 원본 좌표의 정밀도와 우리가 고른 반경이 결정합니다. 정확히 말하면 "셀 경계라는 임의적 절단이 사라진다"입니다.

13.5건물을 통과하는 경로는 별개 문제입니다

섞으면 원인을 못 찾습니다
정상 도로의 주변 시설 점수가 부정확하다     →  H3 공간 집계 문제  (이 문서)
도보망에 없는 직선 경로가 생성된다          →  Graph 생성·결합·표시 문제  (별개)

H3가 기존 Edge에 점수만 붙인다면, H3 자체가 건물을 통과하는 새 길을 만들지는 않습니다. 건물 통과 경로가 보인다면 다음을 따로 조사해야 합니다.

원본 서울시 도보 LINK에 그 Edge가 실제로 존재하는가?
좌표가 가깝다는 이유만으로 서로 다른 노드를 연결했는가?
공원·경사 등의 Line 데이터를 도보 Edge로 추가했는가?
다중 Edge를 일반 Graph로 변환하면서 연결 정보가 달라졌는가?
경로는 정상인데 프론트엔드가 중간 좌표를 생략하고 직선으로 그렸는가?

대표 경로 하나를 골라 원본 LINK까지 역추적하면 어느 단계인지 바로 나옵니다. H3 개선과 동시에 진행하되 원인은 분리해야 합니다.

질문과 답

질문답
왜 H3를 빼나격자는 "같은 칸인가"만 보고 거리를 안 봅니다. 칸이 길보다 11배 커서 길 34.9개가 같은 점수를 받습니다
GiST가 대안 방식인가아닙니다. 거리 계산을 빠르게 하는 색인입니다. 방식은 "거리로 세기", 도구가 GiST입니다
R-tree는 안 쓰나이미 씁니다. PostGIS의 GiST 공간 인덱스가 R-tree 구현입니다. 별도 선택지가 아닙니다
KD-tree는DB 인덱스가 아니라 파이썬 메모리 구조입니다. 지금 H3 방식의 문제가 재발하고, 지구 곡률도 직접 보정해야 합니다
H3로 먼저 걸러 하이브리드로 쓰면GiST가 이미 하는 일과 중복입니다. 코드만 늘고 이득이 없습니다
근거가 무엇인가같은 시설·같은 구역에서 구별값 3개 → 252개. 이미 거리 방식인 공원 겹침이 3,969개(안전 점수의 67배). 인덱스와 코드가 이미 저장소에 있음
성능은Crunchy Data 실측 14초 → 7.8ms (약 1,800배). PostGIS 공식 문서가 GiST를 표준 관행으로 명시
상용 지도 서비스도 쓰나공개 근거 없습니다. 그걸 근거로 쓰면 안 됩니다. 우리 근거는 같은 DB · 배치 작업 · 이미 있는 인프라입니다
위험은반경을 작게 잡으면 점수가 죽습니다. 150~200m + 거리 가중이 필요합니다
H3를 완전히 버리나아닙니다. 점수 계산에서만 뺍니다. 히트맵·구별 통계에는 363m 해상도가 오히려 적합합니다
한 문장 루디는 "H3 셀이 같으므로 관련 있다"는 근사 규칙에서 벗어나, PostGIS로 시설과 기존 도보 Edge의 실제 거리·교차·중첩을 계산해야 합니다. H3는 통계·시각화 용도로만 남기고, 걸을 수 있는지와 경로 연결 구조는 서울시 도보 네트워크만 담당하도록 분리합니다.
다음 단계 CCTV 좌표만 있으면 반경 후보(100 / 150 / 200m)로 실제 점수를 계산해 볼 수 있습니다. 0인 비율과 구별값 개수를 재서 반경을 숫자로 정하면 [근거 없음] 하나가 [근거 있음]으로 바뀝니다.

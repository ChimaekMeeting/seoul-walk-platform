### 1-3. 왜 이 방법을 택했는지 — 판단 근거 2가지

**① `route_schema.py`/`profiles.py`/`route_executor.py`/`extractor.py`를 안 고치고 "임시 호환" 방식을 쓴 이유**

이 4개 파일은 **알고리즘 팀·챗봇 팀이 지금 따로 작업 중인 영역**이라 오늘 손대지 말라는 지시를 받았습니다. 그런데 `user_preferences`의 `TAG_WEIGHT_MAP`(태그→가중치 매핑표)을 지우자, `route_executor.py`와 `extractor.py`가 바로 이 이름을 가져다 쓰고 있어서 **매 대화·매 경로 요청마다 프로그램이 통째로 멈추는(ImportError, "가져오려는 이름이 없다"는 에러) 문제**가 생겼습니다.

그래서 `survey_service.py` 맨 아래에 이렇게 딱 한 줄을 남겨뒀습니다:
```python
# 임시 호환용 — route_executor.py, extractor.py가 이 이름을 import함.
# 실제로는 더 이상 안 쓰임(_resolve_weights가 대체).
TAG_WEIGHT_MAP: dict = {}
```
빈 딕셔너리(dict, "이름표-값" 쌍을 저장하는 자료구조)를 하나 남겨두면, 저 두 파일은 "가져올 이름이 없다"는 에러 없이 계속 동작합니다. 대신 실제로 하던 일(대화 속 테마를 가중치에 반영하는 것)은 **크래시 없이 조용히 아무 효과가 없는 상태**가 됩니다. **완전히 고치는 것보다 "일단 안 죽게만 해두고, 진짜 설계는 알고리즘·챗봇 팀과 같이 맞춘다"는 쪽을 택했습니다** — 남의 작업 영역을 제가 먼저 결정해버리면 나중에 다시 맞추는 비용이 더 커질 수 있기 때문입니다.

**② `nature_layer`는 남기고 `landmark_layer`/`child_layer`/`running_layer`는 지운 이유**

먼저 이 4개 테이블을 실제로 누가 쓰는지 코드를 전부 뒤져봤습니다. 그 결과:
- `nature_layer`는 **`NatureCollector`(삭제 대상) 말고 `ParkPolygonCollector`(서울시 공원 도형을 저장하는, 지금도 살아있는 코드)도 같이 쓰고 있었습니다.** 이 테이블을 지우면 `ParkPolygonCollector`까지 같이 망가지므로, 테이블은 남기고 `NatureCollector.py` 파일만 지웠습니다.
- 4개 테이블 전부 **"지도에 점 찍기용 API"**(`/api/map/points/...`)에도 쓰이고 있었는데, **사용자님이 실제 프론트엔드(Expo 앱, 이 저장소 밖에 있는 진짜 서비스 화면) 코드를 직접 확인해서 "이 API 4개 전부 프론트에서 아예 호출 안 한다"는 걸 확인해주셨습니다.** 그래서 안심하고 `landmark`/`child`/`running` 3개는 API까지 통째로 지울 수 있었습니다.

### 2-3. `safety_score`/`accident_score`는 실제로 어떻게 계산되나

**`safety_score` (안전 점수, 0~1 사이 값, 1에 가까울수록 안전)**
1. CCTV 중 "교통단속·교통정보수집·차량방범" 목적은 제외(보행 안전과 무관하다고 판단)
2. 남은 CCTV + 보안등을 반경 20m로 "버퍼링"(ST_Buffer, 점 하나를 중심으로 반지름 20m 원을 그리는 것)
3. 여러 원이 겹치면 먼저 하나로 합침(ST_Union, "여러 도형을 겹친 부분 없이 하나로 합치기")
4. 합쳐진 도형과 도로가 겹치는 길이를 구함(ST_Intersection, "두 도형이 겹치는 부분만 뽑아내기") → 도로 전체 길이로 나누면 0~1 비율
5. 보안등 데이터 자체가 없는 5개 구(강남·용산·마포·도봉·성동)는 CCTV만으로 계산

**`accident_score` (사고 점수, 0~1 사이 값, 클수록 사고다발지역과 많이 겹침)**
- 반경으로 새로 원을 그리지 않고, 도로교통공단이 제공한 **사고다발지역의 실제 폴리곤(도형) 원본**을 그대로 씀
- 겹치는 폴리곤들을 먼저 합친 뒤(위 3번과 같은 원리), 도로와 겹치는 길이 비율을 구함

**실제 계산 결과 (25개 자치구, safety_score 평균 — 높은 순)**

### 2-4. 실행 검증 — 실제로 발견하고 고친 버그 2가지

**① 순서 버그 (커버리지가 부풀려짐)**
처음 만든 코드는 "안전시설마다 각각 도로와 겹치는 부분을 구한 뒤, 그 조각들을 나중에 합치는" 순서였습니다. 문제는 여러 시설의 원이 겹치는 구간에서, 각각 따로 구한 겹침 조각들이 컴퓨터 계산 오차로 완벽히 딱 안 겹쳐서 **같은 길이가 두 번, 세 번 중복으로 더해지는** 현상이 있었습니다.

- **발견 경위**: 사용자님이 미리 psql(DB에 직접 명령어를 치는 도구)로 계산해둔 "정답"(관악구 0.706)과 제가 만든 코드 결과(0.7307)를 대조했는데 차이가 났고, 실제 psql 쿼리문을 받아 한 줄씩 비교하며 원인을 좁혔습니다.
- **고친 방법**: "먼저 원들을 다 합친 뒤, 도로와 딱 한 번만 겹쳐보는" 순서로 바꿨습니다. 고친 뒤 관악구가 0.7058로 나와서 정답(0.706)과 거의 일치했습니다.
- 같은 실수를 `accident_score` 계산에도 반영해서 같이 고쳤습니다.

**② `replace_types` 버그 (발견만 하고 고치지는 않음)**
`safety_collector.py`의 옛날 사고다발지역 수집 로직(`update_accident()`)에 `safety_types={"streetlight", "cctv"}`를 넘기는 코드가 있었는데, 이건 "사고다발지역 데이터를 넣으면서 엉뚱하게 가로등·CCTV 데이터를 지운다"는 뜻이라 오기로 보입니다. 다만 이 옛날 경로 자체를 새 폴리곤 기반 방식(`accident_collector.py`)으로 완전히 대체했기 때문에, **버그를 고치는 대신 "이제 안 쓰는 코드"라는 주석만 남기고 그대로 뒀습니다.**

## 3. 다른 팀원에게 공유할 내용

> **아래 항목 전부 방금 실제 코드를 다시 열어서 최신 상태 기준으로 확인했습니다.**

1. **`route_schema.py`/`profiles.py`가 폐기된 4축(nature/landmark/running/child) 필드를 여전히 갖고 있습니다.** `Weights` 클래스에 8개 필드 그대로, `ScoringProfile`에도 `NATURE`/`RUNNING`/`LANDMARK`/`CHILD` 4개 프로필이 그대로 있습니다. (건드리지 말라고 하셔서 그대로 뒀습니다.)
2. **`scoring_engine.py`가 이 4축을 읽으려고는 하는데, 이제 항상 0.0으로 고정됩니다.** `data.get("nature_score") or 0.0` 같은 코드라 에러는 안 나지만, 애초에 이 값을 실어서 넘겨주는 쪽(아래 4번)이 없어서 항상 기본값만 나옵니다.
3. **`weights_comfort`는 `Weights`에 필드 자체가 없어서 라우팅(경로 계산)에 전혀 안 쓰입니다.** 온보딩에서 "편안" 선택하면 DB엔 저장되지만, 실제 경로 추천에는 지금 아무 영향이 없습니다.
4. **`safety_score`/`accident_score`가 계산은 끝났지만, `graph_loader.py`(정확히는 그 안의 `GraphRepository`)가 아직 하나도 안 읽습니다.** 코드를 직접 열어봤는데, DB에서 그래프를 불러올 때 `link_id`/`start_node`/`end_node`/`length_m`만 가져오고 **점수 컬럼은 `safety_score`든 `slope_score`든 `accident_score`든 아무것도 select하지 않습니다.** 즉 이건 오늘 작업 때문에 생긴 문제가 아니라 **원래부터 모든 점수가 경로 계산에 반영이 안 되고 있는 상태**입니다 — 다만 오늘 만든 두 점수도 여기 포함된다는 뜻이라 짚어드립니다.

   더 정확히는, **지금 이 환경은 DB를 직접 쿼리하지 않고, 8월 24일에 미리 만들어둔 그래프 파일(`artifacts/walk_graph_v1.pkl`, `.env`의 `WALK_GRAPH_SOURCE=artifact` 설정)을 통째로 불러와서 씁니다.** 그래서 DB에 `safety_score`/`accident_score`/`slope_score`가 다 채워져 있어도 지금 당장은 실제 경로 계산에 반영되지 않습니다. **이건 문제가 아니라 예정된 다음 단계 때문입니다 — 데이터 적재를 마친 뒤 이 파일을 새 데이터 기준으로 다시 구울(재빌드) 계획이 이미 있습니다.** (아래 5-6 "오늘 이후 남은 작업" 표 참고)
5. **`route_executor.py`/`extractor.py`의 `TAG_WEIGHT_MAP` 임시 봉합** — 1-3절에 설명한 그대로, 빈 딕셔너리로 일단 안 죽게만 해뒀습니다. 새 2축 구조에 맞는 진짜 설계가 필요합니다.
6. **`extractor.py`가 매 대화 턴마다 무의미한 LLM(거대언어모델, 챗봇이 답을 생성하는 AI) 호출을 하고 있습니다.** 태그 후보가 빈 리스트인데도 "0~3개 골라라"라고 매번 물어본 뒤 결과를 버립니다. 비용·응답 속도 문제로 이어질 수 있습니다.
7. **프론트(Expo 앱) `survey.ts`가 여전히 8개 가중치 필드로 되어 있을 가능성이 높습니다.** ⚠️ **확인 필요** — 이 파일은 이 저장소 밖에 있어서 제가 직접 열어볼 수 없었습니다. 프론트 팀이 2축(`safety`, `comfort`)에 맞춰 타입을 동기화해야 합니다.
8. **`graph_loader.py` 문서 주석(docstring)이 이미 없어진 컬럼명(`running_score`, `landmark_score`, `child_score` 등)을 그대로 나열하고 있습니다.** 실제 동작(4번 참고)엔 문제없는, 낡은 설명글일 뿐입니다.
9. **`accident_prone_area`, `safety_score`/`accident_score` 관련 코드는 커밋은 되어 있지만(2026-09-15, `8d3fe3d`), origin(팀 공용 저장소)에는 안 올라갔고 `dev` 브랜치에도 아직 안 합쳐졌습니다.** (사용자님 메모와 살짝 다른 부분이라 정정합니다 — "커밋 전"이 아니라 "로컬 커밋은 됐지만 공유 전"입니다.) 오늘(9/16) 진행한 2축 축소·레이어 정리 작업은 **커밋조차 안 된 순수 작업 중 상태**입니다.

## 1. 배경과 목적

순환 경로 탐색 엔진(GRASP/ALNS/Beam 계열)을 비교할 때 지금까지 쓰던 지표(거리 오차, 자기중첩 비율, 실행시간)에는 "이 경로가 걷기에 얼마나 편안한가"를 나타내는 축이 없었다. 회전이 잦은 경로는 걸음을 멈추고 방향을 다시 잡아야 해 보행 리듬이 끊기고 피로해지는데, 이는 안전(safety)·편의(convenience)와는 다른 별도의 문제다.

이 작업의 목표는 **특정 탐색 엔진에 종속되지 않는 진단·비교용 경로 회전량 지표(`turn_cost`)를 만들어, 엔진별 경로 형상 차이를 실측으로 비교할 수 있게 하는 것**이다. 처음부터 엔진의 accept/reject 기준이나 목적함수에는 연결하지 않는다는 전제로 진행했다.

## 2. 설계 — 왜 간단하지 않았는가

**엣지 단위 저장은 불가능했다.** 회전은 도로 하나(엣지)의 속성이 아니라 "직전 도로 + 교차로 + 다음 도로"의 관계에서만 정의된다(경사도와의 핵심 차이). 대안으로 검토한 엣지 굴곡도(길이/직선거리)는 도보 엣지의 74.8%가 정점 2개짜리 직선이라(평균 45.8m, 교차로 간 짧은 토막) 변별력이 없어 폐기했다.

**특정 엔진에 종속시키지 않았다.** 순환 경로 엔진이 여러 종류(Beam/GRASP/ALNS 계열) 공존하는 상태라, 특정 엔진 코드에 회전 계산을 박아 넣으면 엔진이 바뀔 때 버려진다. 그래서 `PathUtils`(엔진 독립 유틸리티 클래스)에 순수 함수로 구현했다.

**여러 차례 기술 검토를 거쳐 다음 문제들을 발견하고 고쳤다.**

| 문제 | 해결 |
|---|---|
| 위경도를 그대로 평면 좌표로 쓰면 동서 방향 왜곡 발생 | curr 노드 위도 기준 등장방형(equirectangular) 투영(`latlon_to_local_xy`) 후 벡터 내적으로 계산 |
| **닫힌 순환 경로에서 회전 1개가 누락되는 버그** | "메인 구간 + 이음매 패치 1개" 방식은 n개 노드 순환에서 n-1개만 계산했다. 전체 노드를 모듈러 인덱스로 순회하도록 수정 — 삼각형 순환(3노드)으로 검증해 정확히 3개가 나오는지 회귀 테스트로 고정 |
| 폐쇄 경로 거리 계산 시 이음매 구간 누락/중복 위험 | `_normalized_nodes`로 시작 노드 중복 여부와 무관하게 정규화, 이음매 거리를 정확히 1회만 포함 |
| 정의 불가 회전(좌표 누락, 0길이 벡터)을 0으로 숨기면 "직진"과 "측정 실패"가 구분 안 됨 | `None` 처리 후 원인별 집계(`undefined_turn_reasons`), 통계에서 별도 필드로 노출 |
| `turn_angles()`가 `(list, dict)` 튜플을 반환해 `max(angles)` 같은 직관적 호출이 깨짐 | 상세 결과(`TurnAngleResult`)와 편의 함수(`turn_angles`→`list[float]`)를 분리 |
| 45°/60°/90° 같은 급회전 임계값을 코어 자료구조에 고정 | 검증된 인간공학적 기준이 아니므로 `TurnMetrics`에 필드로 두지 않고, `count_turns_at_or_above()`로 분석 단계에서 동적 계산하도록 분리 |

**최종 API**

```
거리:  _edge_distance_m → calc_distance → path_distance_m
회전각: latlon_to_local_xy → turn_angle → turn_angle_at → turn_angle_result
편의:  turn_angles → list[float]
통계:  turn_metrics → TurnMetrics
```

## 3. 구현

`src/route_engine/engines/path_utils.py`에 위 API를 추가했다(기존 `calc_distance`는 `_edge_distance_m` 추출 리팩터링만 하고 동작은 그대로 유지). `tests/unit/test_path_utils.py`에 63개 단위 테스트를 추가했다 — 직진/좌우회전/유턴/부동소수점 경계/0길이 벡터/좌표 누락/열린-닫힌 경로/내부 재방문/닫힌 삼각형 회귀 테스트 등을 포함한다.

## 4. 실제 경로 분포 검증

### 4.1 현재 활성 엔진 9종 전수 측정

현재 실제로 쓰이는 **순환 엔진 9종**(`grasp-wp-local/vnd/vns/alns`, `beam-wp`, `beam-wp-local/vnd/vns/alns`)으로 25개 시나리오 전수를 측정했다 — **225/225 전부 성공**(실패 0건), 정의 불가 회전 19,396건 중 0건(0.000%).

**누적 회전량과 급회전 패턴은 다른 정보를 준다.** `beam-wp`는 거리당 회전량이 중위권인데, 90° 이상 급회전 횟수는 **가장 적으면서**(6.9회) 평균 최대 단일회전각은 **가장 크다**(158.0°) — "웬만해선 안 꺾이지만, 꺾일 땐 크게 꺾이는" 유형이다. 단일 지표로 엔진을 줄 세우면 이런 성격을 놓친다.

### 4.2 부수 발견: `grasp-wp-vnd` == `grasp-wp-local` 현상 (조사 완료, 버그 아님)

일부 시나리오에서 `grasp-wp-vnd`가 `grasp-wp-local`과 노드ID까지 완전히 같은 경로를 반환해 원인을 코드로 직접 추적했다. **VND는 실제로 실행되고, GRASP 24회 반복 중 9회에서 Local보다 명백히 나은 경로를 찾는다.** 다만 GRASP의 최종 채택 기준(`repeated_edge_ratio` 우선, `distance_error_m` 차선)에서 뽑힌 "승자 반복"이 하필 VND가 추가 개선을 못 찾은 반복과 우연히 겹쳐서, 최종 결과만 같게 나온 것이었다. 호출 경로·어댑터에는 문제가 없다. `seed=42`·특정 목적함수 설계에 한정된 관측이라 일반화하면 안 된다.

### 4.3 확률적 엔진 식별과 seed 보정

같은 프로세스 반복이 아니라 **실제로 다른 seed**로 재실행해 확인한 결과, 9종 중 3종(`grasp-wp-alns`, `beam-wp-alns`, `beam-wp-vns`)은 seed에 따라 실제로 값이 달라지는 확률적 엔진이었다(`grasp-wp-alns`는 테스트한 모든 시나리오에서, 나머지 2종은 시나리오에 따라 — 한 경우 1.76배 차이). 반면 나머지 6종은 코드상 seed를 읽더라도 테스트 범위에서는 결과가 바뀌지 않았다(실질적으로 결정적).

이 3종을 대표할 수 있는 값을 얻기 위해 `benchmarks/config.py::BENCHMARK_SEEDS`(팀이 이미 분산 추정용으로 정해둔 시드 10개)로 25개 시나리오 전수를 재측정했다(750/750 성공). 그 결과 **`beam-wp-vns`가 seed=42 단일값(845.4, 9종 중 최하위)으로는 "가장 회전이 잦은 엔진"처럼 보였지만, 10개 시드 평균(794.6, 95% 신뢰구간 [765.7, 823.4])으로는 중위권으로 올라왔다** — 단일 시드 관측이 우연히 나쁜 쪽으로 치우쳐 있었던 것이다.

### 4.4 임계값(30~120°) 민감도 분석

전체 19,396건 기준 회전각 분포: 45° 이상은 32.4%(흔함), 90° 이상은 9.1%, 120° 이상은 0.68%(뚜렷한 극단값).

**30~60° 기준으로는 9개 엔진 순위가 거의 안정적**이지만, **75° 이상부터 순위가 크게 흔들린다.** `beam-wp`가 대표 사례다 — 30~60° 기준 3위(중위권) → 90° 기준 1위(급회전 최소) → 120° 기준 9위(최다)로 **같은 데이터, 다른 임계값에서 정반대 결론**이 나온다. §4.1의 "최대 단일회전각이 가장 크다"는 발견과 정확히 들어맞는다 — 하나의 임계값만 보고 엔진을 비교하면 안 된다는 걸 데이터로 재확인했다.

## 6. 부수적으로 발견·처리한 것

- **`docs/route_engine/README.md` 갱신**: `PathUtils`에 추가한 turn_cost API가 이 저장소의 Current 계약 문서에 반영돼 있지 않았다. 기존 문서 형식(날짜별 절)에 맞춰 "방향 전환(turn_cost) 진단 지표" 절을 추가했다.
- **`graph_loader.py`의 낡은 docstring 수정**: `load_route_graph()`가 실제로 반환하는 node/edge 속성(node: `lon`/`lat`만, edge: `link_id`/`length`/`toilet_count`/`transit_count`/`accessibility_poi_count`만)과 docstring에 적힌 속성(`node_type`/`is_underground`/`is_overpass`, `safety_score`/`nature_score`/`slope_score` 등)이 어긋나 있었다. 팀원이 컬럼을 정리하면서 docstring을 갱신하지 않은 것으로 보인다. 동작 변경 없이 docstring만 실제 구현에 맞게 고쳤다.
- **`beam-circular` 벤치마크 어댑터 버그**: 초기에 legacy 순환 엔진으로 잘못 측정하던 중 발견했으나, `beam-circular`가 commit `4c7c924`로 이미 `SOLVER_REGISTRY`에서 빠져 아무 데서도 안 쓰이는 죽은 코드임을 확인했다. 수정은 철회했고, 이슈 등록도 하지 않았다(등록해도 아무도 안 쓸 코드).

## 7. 최종 결론

1. **`turn_cost`는 실제 서울 도보 그래프·9개 엔진·25개 시나리오에서 정상 동작한다.** 정의 불가 케이스 0건, 회귀 테스트(닫힌 삼각형 3개 회전)로 핵심 버그도 막아뒀다.
2. **엔진 간 회전 형태 차이는 크지 않고, 9종 중 8종은 통계적으로 뚜렷이 구분되지 않는다.** 확실히 다른 건 `grasp-wp-vns`(가장 완만) 하나뿐이다. 어떤 지표(누적 vs 급회전)·어떤 임계값을 쓰느냐에 따라서도 "어느 엔진이 더 편안한가"의 답이 달라질 수 있다.
3. **확률적 엔진 3종은 단일 실행값으로 비교할 수 없었다** — 10개 시드로 재측정해 보정했고, 특히 `beam-wp-vns`의 "최하위" 평가는 착시였음을 확인했다.
4. **45/60/90/120° 같은 임계값은 여전히 잠정치다.** 실제 보행 속도·주관적 불편도 등 사용자 행동 데이터와의 상관관계는 검증되지 않았고, 그런 데이터 자체가 없어 계속 보류 상태다.
5. **회전량은 아직 엔진 선택의 목적함수에 연결되지 않았다.** 지금까지는 순수 진단·비교 지표다.

## 8. 남은 과제 (우선순위 순)

1. 사용자 행동 데이터(보행 속도, 재탐색 횟수, 주관적 불편도 등)를 확보해 45/60/90° 후보 중 실제로 의미 있는 임계값이 있는지 검증한다.
2. 순환 엔진이 최종 확정되면, 그때 `turn_cost`를 해당 엔진의 목적함수 또는 정렬 기준에 실제로 연결할지 판단한다.
3. (낮은 우선순위) 엣지 내부 형상(geometry, 굽은 도로의 shape point)을 반영해야 하는 사례가 실제로 관측되면, 그때 노드 단위 계산을 확장한다.
4. (선택) p50/p90/45~90°↑ 등 세부 분포 열까지 다중 시드로 보정하려면 원본 회전각을 저장하는 추가 실행이 필요하다 — 필요성이 확인되면 진행한다.

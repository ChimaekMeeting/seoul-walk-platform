**세부 데이터**: [README.md](README.md), [turn_cost_distribution.csv](turn_cost_distribution.csv), [variance_sample/](variance_sample/)

## 1. 배경과 목적

순환 경로 탐색 엔진(GRASP/ALNS/Beam 계열)을 비교할 때 지금까지 쓰던 지표(거리 오차, 자기중첩 비율, 실행시간)에는 "이 경로가 걷기에 얼마나 편안한가"를 나타내는 축이 없었다. 회전이 잦은 경로는 걸음을 멈추고 방향을 다시 잡아야 해 보행 리듬이 끊기고 피로해지는데, 이는 안전(safety)·편의(convenience)와는 다른 별도의 문제다.

이 작업의 목표는 **특정 탐색 엔진에 종속되지 않는 진단·비교용 경로 회전량 지표(`turn_cost`)를 만들어, 엔진별 경로 형상 차이를 실측으로 비교할 수 있게 하는 것**이다. 처음부터 엔진의 accept/reject 기준이나 목적함수에 연결하지 않는다는 전제로 진행했다.

## 2. 설계 — 왜 간단하지 않았는가

### 2.1 엣지 단위 저장은 불가능했다

회전은 도로 하나(엣지)의 속성이 아니라 "직전 도로 + 교차로 + 다음 도로"의 관계에서만 정의된다(경사도와의 핵심 차이). 대안으로 검토한 엣지 굴곡도(길이/직선거리)는 도보 엣지의 74.8%가 정점 2개짜리 직선이라(평균 45.8m, 교차로 간 짧은 토막) 변별력이 없어 폐기했다.

### 2.2 특정 엔진에 종속시키지 않았다

순환 경로 엔진이 여러 종류(Beam/GRASP/ALNS 계열) 공존하는 상태라, 특정 엔진 코드에 회전 계산을 박아 넣으면 엔진이 바뀔 때 버려진다. 그래서 `PathUtils`(엔진 독립 유틸리티 클래스)에 순수 함수로 구현했다.

### 2.3 여러 차례 기술 검토를 거쳐 확정한 설계

다음 문제들을 검토 과정에서 발견하고 고쳤다.

| 문제 | 해결 |
|---|---|
| 위경도를 그대로 평면 좌표로 쓰면 동서 방향 왜곡 발생 | curr 노드 위도 기준 등장방형(equirectangular) 투영(`latlon_to_local_xy`) 후 벡터 내적으로 계산 |
| **닫힌 순환 경로에서 회전 1개가 누락되는 버그** | "메인 구간 + 이음매 패치 1개" 방식은 n개 노드 순환에서 n-1개만 계산했다. 전체 노드를 모듈러 인덱스로 순회하도록 수정 — 삼각형 순환(3노드)으로 검증해 정확히 3개가 나오는지 회귀 테스트로 고정 |
| 폐쇄 경로 거리 계산 시 이음매 구간 누락/중복 위험 | `_normalized_nodes`로 시작 노드 중복 여부와 무관하게 정규화, 이음매 거리를 정확히 1회만 포함 |
| 정의 불가 회전(좌표 누락, 0길이 벡터)을 0으로 숨기면 "직진"과 "측정 실패"가 구분 안 됨 | `None` 처리 후 원인별 집계(`undefined_turn_reasons`), 통계에서 별도 필드로 노출 |
| `turn_angles()`가 `(list, dict)` 튜플을 반환해 `max(angles)` 같은 직관적 호출이 깨짐 | 상세 결과(`TurnAngleResult`)와 편의 함수(`turn_angles`→`list[float]`)를 분리 |
| 45°/60°/90° 같은 급회전 임계값을 코어 자료구조에 고정 | 검증된 인간공학적 기준이 아니므로 `TurnMetrics`에 필드로 두지 않고, `count_turns_at_or_above()`로 분석 단계에서 동적 계산하도록 분리 |

### 2.4 최종 API

```
거리:  _edge_distance_m → calc_distance → path_distance_m
회전각: latlon_to_local_xy → turn_angle → turn_angle_at → turn_angle_result
편의:  turn_angles → list[float]
통계:  turn_metrics → TurnMetrics
```

## 3. 구현

`src/route_engine/engines/path_utils.py`에 위 API를 추가했다(기존 `calc_distance`는 `_edge_distance_m` 추출 리팩터링만 하고 동작은 그대로 유지). `tests/unit/test_path_utils.py`에 63개 단위 테스트를 추가했다 — 직진/좌우회전/유턴/부동소수점 경계/0길이 벡터/좌표 누락/열린-닫힌 경로/내부 재방문/닫힌 삼각형 회귀 테스트 등을 포함한다.

## 4. 실제 경로 분포 검증 — 두 번 다시 만든 이유

### 4.1 1차 시도에서 발견한 것: 이미 폐기된 엔진을 측정하고 있었다

처음에는 당시 로컬 브랜치(`feat/grasp-waypoint-alns-comparison` 기준, `dev`보다 오래된 상태)의 `SOLVER_REGISTRY`를 그대로 써서 `beam-circular`/`grasp-circular`/`alns-circular`/`rcsp-circular`(legacy 순환 4종) + `grasp-wp-local`로 25개 시나리오를 측정했다.

그런데 `dev`를 최신화하는 과정에서, 이 legacy 4종 중 3종(beam/grasp/alns-circular)이 **같은 날짜에 이미 팀이 폐기 결정한 엔진**이었다는 걸 뒤늦게 확인했다(commit `4c7c924`, "레거시 순환 4종... 되살릴 계획이 없다 — 신세대 9종으로 대체됐다"). `beam-circular`의 벤치마크 어댑터(`beam_solver.py`)도 이미 `benchmark.py`가 import하지 않는 죽은 코드였다. 처음 발견했던 "beam-circular 어댑터가 `TypeError`로 항상 실패한다"는 버그도, 알고 보니 아무도 안 쓰는 코드의 버그였다 — 수정을 시작했다가 이 사실을 확인하고 철회했다.

### 4.2 브랜치를 최신화하고 재측정

`feature/turn-cost-metric`을 `dev`(`331cad6`)에 병합해 최신 상태로 맞췄다(충돌은 `path_utils.py` import 줄 1곳뿐, 나머지는 자동 병합됨 — 병합 과정에서 기존에 실패하던 `find_nearest_node` 테스트도 `dev`가 이미 고쳐놔서 해결됨). 이 과정에서 `git stash pop`을 잘못 실행해 무관한 스태시가 섞이는 사고가 있었으나, 스태시 자체는 보존한 채 영향받은 6개 파일만 원래 상태로 복구했다(`dev`와 바이트 단위로 동일함을 재확인).

현재 실제로 쓰이는 **순환 엔진 9종**(`grasp-wp-local/vnd/vns/alns`, `beam-wp`, `beam-wp-local/vnd/vns/alns`)으로 25개 시나리오 전수를 다시 측정했다 — **225/225 전부 성공**(실패 0건, legacy 때는 alns 2건 실패했던 것보다 안정적).

### 4.3 핵심 결과

| 항목 | 값 |
|---|---|
| 거리당 회전량 범위 | 740.7 ~ 845.4 °/km (9종 간 격차 1.14배 — legacy 4종 때의 1.7배보다 훨씬 좁음) |
| 가장 완만 | `grasp-wp-vns` |
| 가장 잦음 | `beam-wp-vns` |
| 정의 불가 회전 | 19,396건 중 0건(0.000%) |

**누적 회전량과 급회전 패턴은 다른 정보를 준다.** `beam-wp`는 거리당 회전량이 중위권(9종 중 6위)인데, 90° 이상 급회전 횟수는 **가장 적으면서**(6.9회) 평균 최대 단일회전각은 **가장 크다**(158.0°) — "웬만해선 안 꺾이지만, 꺾일 땐 크게 꺾이는" 유형이다. 단일 지표로 엔진을 줄 세우면 이런 성격을 놓친다.

### 4.4 부수 발견: `grasp-wp-vnd` == `grasp-wp-local` 현상 (조사 완료, 버그 아님)

일부 시나리오에서 `grasp-wp-vnd`가 `grasp-wp-local`과 노드ID까지 완전히 같은 경로를 반환해 원인을 코드로 직접 추적했다. **VND는 실제로 실행되고, GRASP 24회 반복 중 9회에서 Local보다 명백히 나은 경로를 찾는다.** 다만 GRASP의 최종 채택 기준(`repeated_edge_ratio` 우선, `distance_error_m` 차선)에서 뽑힌 "승자 반복"이 하필 VND가 추가 개선을 못 찾은 반복과 우연히 겹쳐서, 최종 결과만 같게 나온 것이었다. 호출 경로·어댑터에는 문제가 없다. `seed=42`·특정 목적함수 설계에 한정된 관측이라 일반화하면 안 된다.

### 4.5 반복 실행 분산 확인 — 3종은 진짜 확률적이다

같은 프로세스 반복이 아니라 **실제로 다른 seed(42/7/123)**로 3개 대표 시나리오를 재실행했다.

| 결과 | 엔진 |
|---|---|
| seed에 따라 항상 값이 바뀜(진짜 확률적) | `grasp-wp-alns` (3/3 시나리오) |
| 종종 크게 바뀜(한 시나리오에서 1.76배 차이) | `beam-wp-alns`, `beam-wp-vns` |
| 테스트한 범위에서 seed 영향 없음(실질적으로 결정적) | 나머지 5종 + `beam-wp` |

즉 §4.3의 "엔진별 회전량 통계" 표에서 **`grasp-wp-alns`/`beam-wp-alns`/`beam-wp-vns` 3종의 값은 seed=42 하나의 관측일 뿐 대표값이 아니다.** 이 3종을 정말 비교하려면 여러 seed로 반복 측정한 평균을 써야 한다(후속 과제로 남김).

### 4.6 임계값(30~120°) 민감도 분석

전체 19,396건 기준 회전각 분포: 45° 이상은 32.4%(흔함), 90° 이상은 9.1%, 120° 이상은 0.68%(뚜렷한 극단값).

**30~60° 기준으로는 9개 엔진 순위가 거의 안정적**이지만, **75° 이상부터 순위가 크게 흔들린다.** `beam-wp`가 대표 사례다 — 30~60° 기준 3위(중위권) → 90° 기준 1위(급회전 최소) → 120° 기준 9위(최다)로 **같은 데이터, 다른 임계값에서 정반대 결론**이 나온다. §4.4의 "최대 단일회전각이 가장 크다"는 발견과 정확히 들어맞는다 — 하나의 임계값만 보고 엔진을 비교하면 안 된다는 걸 데이터로 재확인했다.

## 5. 최종 결론

1. **`turn_cost`는 실제 서울 도보 그래프·9개 엔진·25개 시나리오에서 정상 동작한다.** 정의 불가 케이스 0건, 회귀 테스트(닫힌 삼각형 3개 회전)로 핵심 버그도 막아뒀다.
2. **엔진 간 회전 형태 차이는 실재하지만 크지 않다**(1.14배). 다만 어떤 지표(누적 vs 급회전)·어떤 임계값을 쓰느냐에 따라 "어느 엔진이 더 편안한가"의 답이 달라질 수 있다.
3. **`grasp-wp-alns`/`beam-wp-alns`/`beam-wp-vns` 3종은 확률적이라 단일 실행값으로 비교하면 안 된다.**
4. **45/60/90/120° 같은 임계값은 여전히 잠정치다.** 실제 보행 속도·주관적 불편도 등 사용자 행동 데이터와의 상관관계는 검증되지 않았고, 그런 데이터 자체가 없어 계속 보류 상태다.
5. **회전량은 아직 엔진 선택의 목적함수에 연결되지 않았다.** 지금까지는 순수 진단·비교 지표다.

## 6. 남은 과제 (우선순위 순)

1. `grasp-wp-alns`/`beam-wp-alns`/`beam-wp-vns` 3종을 여러 seed로 반복 측정해 대표값(평균·분산)을 확보한다.
2. 사용자 행동 데이터(보행 속도, 재탐색 횟수, 주관적 불편도 등)를 확보해 45/60/90° 후보 중 실제로 의미 있는 임계값이 있는지 검증한다.
3. 순환 엔진이 최종 확정되면, 그때 `turn_cost`를 해당 엔진의 목적함수 또는 정렬 기준에 실제로 연결할지 판단한다.
4. (낮은 우선순위) 엣지 내부 형상(geometry, 굽은 도로의 shape point)을 반영해야 하는 사례가 실제로 관측되면, 그때 노드 단위 계산을 확장한다.
